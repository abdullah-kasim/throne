# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Read `AGENTS.md` and your role's file (`agent_docs/role-<role>.md`, named in its "Role files" index) before making changes. It is the authoritative operating contract for the Lord → Regent → Alpha → Shadow hierarchy, delegation boundaries, objective-coded campaign names, worktree isolation, and model-routing policy. In particular, agents never ask the Lord to resolve decisions: Alphas research and decide, while the Regent reports outcomes.

AGENTS.md is not self-contained: it repeatedly defers detail to `agent_docs/*.md` — `agent_docs/architecture.md` (durable law's second half), `agent_docs/MODEL_POLICY.md`, `agent_docs/commands.md`, and `agent_docs/rest-transport-migration.md` among them. Read the one the current task touches, not just AGENTS.md.

## Commands

Production executes compiled JavaScript from `dist/` on the Bun pinned in
`mise.toml`, started through `bin/throne-runtime`, the one place that names the
runtime. Running the TypeScript sources directly does not provide the Nest
decorator transform or runtime metadata. Build with `bun run build`, then run
`bun run start` (or `./bin/throne-cli <command>`).

```bash
# Run the compiled CLI (omit the command to print the complete command surface)
bun run start -- <command>

# Static type checking
bun run typecheck

# Lint (eslint + the public-release private-reference backstop); both gate `bun run test`
bun run lint
bun run lint:private-refs

# Full test suite
bun run test

# Heavy real-infrastructure tests (canaries + real-systemd rollback proof).
# LORD'S DIRECT ORDER ONLY — no agent runs this or sets THRONE_HEAVY_TESTS
# on its own initiative. See AGENTS.md "Hard rules of the court".
bun run test:heavy

# Web app: hot reload against a running listener, and its Vitest tests (`bun run test` runs them too)
bun run dev:web
bun run test:web

# Playwright end-to-end tests of the where-i-stand page against the fixture backend.
# A separate pre-merge gate: `bun run test` does not run them (the suite image has no browser). Needs `bun run build`.
bun run test:e2e

# Where-i-stand evidence: product and reference captures, contact sheet and evidence.json per preset
bun scripts/where-i-stand-evidence/run.mjs --preset <name|all> --out <folder> --port <port> --data-home <folder>

# Run one named test (bypasses the suite guards below — use `bun run test` before calling work done)
bun test --test-name-pattern='a features file that names an unknown flag is still refused' ./src/shared-policy/feature-flags.service.spec.ts
```

`bun run test` is not a bare `bun test`: it runs through `scripts/run-suite-container.mjs` inside a container under whichever OCI runtime the host has (docker, then podman; `THRONE_CONTAINER_RUNTIME` forces one), which enforces a `dist-staleness-guard` (a stale `dist/` fails the suite — rebuild) and a `herdr-tab-leak-guard` before and after the run (a leaked herdr tab fails it). The single-test form above skips all of that.

The Nest sources use legacy decorators with emitted design-time metadata, so
`tsc` still emits `dist/`; only the compiled build is production evidence.

## Architecture

`src/tools.ts` is a thin entrypoint into the Nest Commander application: every user-facing command is owned by a command module under `src/`. Those command modules compose shared domain modules rather than duplicating their policies.

Herdr responsibilities are owned by modules under `src/` and consumed directly by Nest Commander domains. Agent addressing is name-based and must resolve uniquely. Message delivery is serialized per recipient pane and uses harness-specific screen evidence so a resident human draft is never overwritten and an uncertain submission is never blindly resent.

`web/` is one Vite and React app, a route per tool, built into `dist/web/` in the same atomic publish as the Nest output. The `src/web-listener/` Nest application inside throne-backend serves it and `/api/<tool>/...` on loopback only (port 8430, `THRONE_WEB_PORT` overrides), and a hosted worker publishes it at `/throne` with `tailscale serve`, tailnet only. A failed bind or a missing tailscale is logged and never stops the backend. Request and response schemas live in `src/web-api-contract/`, imported by both sides. A new tool is a folder under `web/src/features/` and one entry in `web/src/app/tools.tsx`. `web/src/components/ui/` is generated by shadcn and exempt from the 500-line limit.

Agent creation separates policy from effects. `src/config.ts` contains declarative model pools and steering data, while the Nest Commander harness-routing domains own fresh-spawn usage, capability, admission, and steering decisions. The `create-agent` command validates the result, persists identity and spawn evidence, then launches through `src/harness.ts`. Capability floors and role-pool admission remain hard gates outside the steering engine.

Campaign code always lives in external git worktrees under `~/.throne/worktrees/<repo-basename>/`, including campaigns that modify the throne itself. The Stager is the one role exempt from campaign isolation: it commits directly in its own tree under `~/.throne/worktrees/throne/<stager-name>`, outside any gate chain, and the prompt hook fast-forwards that tree to `main` before each prompt (`agent_docs/role-stager.md`). The gitignored `data/<agent-name>/` ledger remains in the live throne checkout and records identity, spawn recipes, target-repository provenance, todo bundles, and recovery evidence. Shadows branch from their Alpha; completed slices merge into the Alpha branch before the campaign is merged once into its recorded target branch.

Systemd user timers only keep the Regent alive and deliver nudges. Durable ledger state, not process presence alone, drives startup reconciliation after a reboot.
