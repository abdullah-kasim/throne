# Agent messaging
Summary: Delivers one message to a named agent pane, wrapped in its queue id tags, without overwriting a draft the pane already holds, over the agent's own delivery socket when it was launched with one (throne's Claude Code mod or pi extension listening on it), can force a bare Enter into that pane, and takes over a pane lock held longer than a minute.

## What it does

Agents talk to each other by name. `send-agent` resolves the name to exactly one herdr pane, queues the text, and the backend delivers it serialized per recipient, reading the harness screen first so a human draft is never overwritten and an uncertain submission is never resent blindly.

Every queued delivery, delivery notices included, is typed as three parts: a line `<messageN>`, the sender-attributed text, and a line `</messageN>`, where N is the queue row id. Paths that never enqueue (the throne-bot bridge, for one) type the text with no tags.

After a queued delivery the backend schedules a receipt check that reads the recipient's transcript and grades the message `intact`, `truncated` or `absent`. A transcript turn holding both tags of that id and the whole typed text is intact; one holding only one tag, or both without the whole text, is truncated. Paste wrappers such as Claude's `<pasted_content …>` fold are ignored when looking for the tags. A transcript with no tag for the id falls back to the older form, a trailing `[message N]`, so messages typed before the change still grade.

Herdr reads, lists, process-info, text sends and key presses go over herdr's socket with no process launch, for the pinned herdr binary. The `herdr` command is the fallback when the socket is unreachable, its ping fails, or a reply says the server changed; a herdr refusal is surfaced unchanged, never retried on the command line. A write whose socket reply is lost fails as `socket_outcome_unknown` and is never resent. Herdr's compatibility check runs once per process and again only when the herdr binary changes, the session name changes, or a herdr call fails saying the server changed (`server_not_running`, `server_unavailable`, `protocol_mismatch`); a foreign or incompatible server is refused on every call.

A Claude Code or pi recipient whose `spawn.json` records `delivery_socket` gets the message over that Unix socket, which the agent listens on and throne connects to (`extensions/shared/agent-delivery-contract.ts` holds every name, shape and bound below). The path is chosen at launch under the real throne home, at most 100 bytes, and passed as `THRONE_DELIVERY_SOCKET`. pi listens inside `extensions/pi/throne-pi-delivery.ts`; the Claude mod in `extensions/claude/` cannot listen, so it starts a helper through `bin/throne-runtime` by absolute path (`THRONE_DELIVERY_RUNTIME`, `THRONE_DELIVERY_HELPER`), restarts it, at most once a second, when it has not reported listening within 5000 ms or is gone, and hears each request from it as one JSON line, answering with `POST /result` within 5000 ms; a mod that sends no result in that time ends the request `busy` and is not asked again, since only an explicit not-yet from the mod is asked again. Both serve the one shared listener in `extensions/shared/agent-delivery-listener.ts`. throne first asks the socket `GET /alive`. An agent whose answer carries `callbacks: true` gets `POST /deliver` with `{ id, pane, text, waitMs, acknowledge: true }`, the id `message-<n>` for queue row n, and answers `accepted` at once when the request is valid, for its own pane and not a repeat; the sender waits at most 1500 ms for that answer and asks again with the same id, up to three times, when the connection drops or no answer comes, and the 500-id repeat rule answers a second ask. `accepted` ends the attempt and moves the row from in-flight to `accepted`; no delivery to such an agent holds a connection while the agent is busy (measured under a second, never over 2 seconds). The agent then owns the message: it works through its accepted messages one at a time in arrival order and lets the harness queue them. The Claude mod submits the prompt even while a turn runs or a draft sits in the box; Claude Code queues it behind the running turn, keeps queued prompts in the order sent, and leaves the draft in the box untouched (measured on 2.1.326). The mod's submit resolves when the prompt enters the session, so a message queued behind a turn is called back delivered when that turn ends. pi saves a draft, clears the box, sends the message (as a follow-up behind a running turn) and puts the draft back. Once the harness has taken the message, the agent posts the outcome `{ id, pane, status, as?, detail? }`, `status` `delivered` or `refused`, to `/api/delivery-callback` on the backend's own unix socket, once per accepted message, every 2 s for up to 2 minutes until the backend answers, then drops it. That socket is `<throne home>/delivery-callback.sock`, given to the agent at launch as `THRONE_DELIVERY_CALLBACK` beside `THRONE_DELIVERY_SOCKET` and recorded in `spawn.json` as `delivery_callback`; the Claude mod calls back from its helper, which runs under Bun, and pi from its extension, under Node. An agent launched without that variable offers no callbacks, and so does every agent launched before this protocol; those keep the held request below until `/restart-harnesses` relaunches them.

The held request: throne posts `{ id, pane, text, waitMs }` with no `acknowledge` and holds the connection open: connecting is bounded by 1000 ms and the answer by `waitMs` plus 2000 ms. The agent refuses a request for another pane, one over 1 MB, one whose body is not read within 5000 ms, and a second request on the same connection; it submits as above and answers `delivered` with `as` `turn` or `followUp` only after the harness took it (pi: its `message_start` for that user text, or `turn_start` for one sent while idle, and a follow-up as soon as pi has queued it; the mod: its submit resolving with no drop). An id among its last 500 delivered is answered `delivered` with `repeat: true` and not submitted again. When the box cannot be read or a draft cannot be set aside, it keeps trying until `waitMs` passes, then answers `busy` with the reason (`draft`, `turn-running`, `composer-unreadable`) and never submits it later; a sender that closes early withdraws it. `delivered` is recorded delivered and `refused` refused. `busy`, or no answer from an agent that still answers `GET /alive`, leaves the message not sent this attempt and types nothing, so the queue tries again. A connection that drops after the request was sent is taken as delivered and never typed, since the agent may already have submitted it. While the agent answers, the delivery holds no pane lock, reads no pane and presses no key, so a human draft is never touched, and the body carries the same sender and `<messageN>` wrapper as the typed path. A socket that cannot be connected to, or a `GET /alive` not answered within 1000 ms, means the agent is not answering, whatever file sits at the path: the message is typed through herdr exactly once, taking the pane lock, with one fallback line naming the agent and the reason; a pi pane is typed into only once its composer reads empty, and a retry of the same message logs no second fallback line. An opening prompt to a new Claude Code or pi agent first asks its socket `GET /alive` every 500 ms for up to 20 seconds (`SOCKET_STARTUP_WAIT_MS`) until it answers, then delivers; every other message to a silent agent is typed at once. `POST /deliver` also carries a harness command (`{ id, pane, command, args, waitMs }`, the id `command-<random>`), which the mod runs as a Claude Code command, only for an agent whose `GET /alive` answer `{ pane, harness, commands }` says `commands: true` (BE-SETTINGS); the pi extension also answers `commands: true`, takes only `color` and `rename`, hands each to the pi look as a `throne:agent-setting` event and answers `delivered` at once, and refuses any other command (LOOK-EVENT); a command that arrives while a turn runs is answered `busy` with `turn-running` at once and not run. The mod remembers the last 500 ids it started, commands and messages alike, and never runs or submits one twice, answering a repeat with the first run's result once it is known. Every other recipient takes the typed path unchanged. Agents launched before the socket keep typed keys until `/restart-harnesses` relaunches them onto one, and live agents gain the accepted answer and the callback at their next `/restart-harnesses`.

The `features.sendAgentFileBackedPayloads` switch in `config.user.ts`, off by default and read the same fresh, tolerant way, stages a body of 768 bytes or more in a file and types a pointer to it instead of the body. Long texts are staged as payloads that `read-payload` reads once and deletes. `mcq` answers or dismisses an interactive prompt holding up a pane, for the Regent or a Stager. `send-agent-legacy` is the synchronous fallback that predates the queue.

`send-agent <name> --enter-only` is the forced Enter. It runs in the caller's own process, with or without `--direct`, and queues nothing. It reads the input box once, capped at 5 seconds. A box covered by a dialog is refused; a box that cannot be read is refused when the harness has a supported screen reader; otherwise one Enter key is sent through herdr's send-keys, taking, checking and waiting on no lock, typing nothing and not reading the box again. A press prints one line and exits 0; a refusal prints the reason and exits 1. The no-idling sweep calls the same function (WD-STUCK-DRAFT).

A delivery writes and presses Enter while holding the recipient pane's lock, and that lock lasts a minute at most (`PANE_LOCK_MAXIMUM_HOLD_MS = 60_000`). The lock is a row in `locks.sqlite3` (see the lock rows spec) holding the holder's process id, start time and the time it was taken; a holder whose process has died frees it at once. A sender that finds the lock held reads that age: under a minute it waits until the lock is released or turns a minute old; at a minute it takes the lock over. The takeover presses the forced Enter on whatever sits in the box (refused only by a dialog or an unreadable box, after which the delivery follows its ordinary rules), replaces the row with the sender's own, logs one line naming the pane, the old process id and the lock's age, and delivers. While another sender holds the lock, a delivery skips its wait for a resident draft to clear before the lock, so the takeover is reached; the draft is handled under the lock. The displaced holder checks it still owns the row before every write and every Enter, stops at once when it does not, and its delivery fails as taken over after a minute and is never retried.

## Sub-features

- MSG-NAME: A target name must resolve to exactly one agent or the send is refused.
- MSG-DRAFT: A draft already waiting in the input box is kept, not overwritten; a message over the delivery socket is submitted beside it (the Claude mod leaves the draft untouched, pi saves and puts it back); the exceptions are `--enter-only` and the no-idling sweep, which press Enter on it (MSG-ENTER-ONLY, WD-STUCK-DRAFT).
- MSG-ENTER-ONLY: `--enter-only` presses one Enter at once, ignoring the recipient lock and any queued delivery, and refuses when a dialog covers the box or a supported harness's box cannot be read.
- MSG-LOCK-EXPIRY: A sender waits for a held pane lock until it is a minute old or released, then takes it over with the forced Enter and delivers; the displaced holder writes nothing more and its delivery fails without a retry.
- MSG-TAGS: A queued delivery is typed between `<messageN>` and `</messageN>` lines carrying its queue id.
- MSG-RECEIPT: The receipt check grades a delivery intact, truncated or absent from its tags, falling back to a trailing `[message N]`; for an accepted message it is scheduled when the agent's delivered callback arrives.
- MSG-HERDR-SOCKET: Herdr calls go over its socket, falling back to the command only when the socket is unreachable or the server changed; a lost write reply is never resent.
- MSG-HERDR-COMPAT: The herdr compatibility check is remembered until the binary, session or server changes; refusals stay.
- MSG-CLAUDE-MOD: A Claude agent launched with the mod gets its message over its delivery socket through the mod's helper with no pane read or key; the helper answers `accepted` at once, the mod submits it even mid-turn for Claude Code to queue in order, and the helper calls the backend's callback socket back with the outcome; an agent launched before this, until its next `/restart-harnesses`, is answered on the same held connection; an opening prompt waits up to 20 seconds for the socket to answer before falling back; a busy agent leaves the message for the queue to retry, a connection dropped after sending counts as delivered, and a silent or unreachable socket falls back to typed keys exactly once with one fallback line.
- MSG-PI: A pi recipient gets the message once over its delivery socket, which its extension listens on, keyed by the queue id so a repeat is not submitted again; it answers `accepted` at once, saves and restores a draft around the submit, and calls the backend's callback socket back with the outcome; a follow-up behind a running turn counts as delivered once pi queues it; an opening prompt waits up to 20 seconds for the socket to answer; a silent or unreachable socket falls back to typed keys exactly once with one fallback line, typed only once the composer reads empty.
- MSG-PAYLOAD: A staged payload is read once and then deleted.
- MSG-MCQ: A held prompt can be answered or dismissed by the Regent or a Stager.
- MSG-LEGACY: The legacy path delivers without the queue.

## How to reach it and prove it works

From a herdr session: `throne send-agent <name> "<text>"` prints a message id; `throne message-status <id>` reaches a delivered state and the text appears in the target pane between `<messageN>` and `</messageN>`. `throne send-agent <name> --enter-only` prints `send-agent: pressed Enter in "<name>"'s input box` and the text left in that box is submitted, even while another process holds the pane's lock. A send started when another process has held the pane's lock for over a minute, with text in the box, submits that text first and then delivers the new message whole within 15 seconds; started at 20 seconds, it waits until the lock is released or a minute old. ## Gotchas

A name that matches two panes is refused rather than guessed. Delivery needs the backend running; without it messages wait in the queue; `--enter-only` does not need it. Claude folds a long paste into a chip and wraps it in `<pasted_content …>` with leading blank lines, so the delivered turn does not start with `<messageN>`. The three-line form is proven on a real Claude pane only; Codex was not signed in on this host when it was recorded. A message that quotes a paste tag literally can still grade truncated, because the transcript escapes those tags. A Claude menu such as `/model` reads as an unreadable box, so `--enter-only` refuses it with "could not be read" rather than "a dialog covers". `--enter-only` presses even when the box is empty. Only deliveries bind the takeover to the forced Enter; other code that takes the pane lock (model switching, spawn recovery, harness command typing, `mcq`, a bare pane write) takes an expired lock over without pressing Enter. A displaced holder's later release deletes nothing, because a release only removes the row it still owns. Claude Code shows the model a mod-delivered message as `The <mod name> plugin sent a message:` above the usual body (measured on 2.1.322). Turning the switch off leaves the mod loaded in live agents, doing nothing.
