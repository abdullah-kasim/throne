## What it does

Policy and effects are separate. `src/config.ts` declares model pools and steering; harness routing decides usage, admission and steering for a fresh spawn; `create-agent` validates the result, persists identity and spawn evidence in the ledger, and launches the harness in a herdr pane. Models carry no capability grades: role-pool admission is the only model gate. Without `--model`, the agent launches on the first model of its role's active pool, exactly as if that model had been named, and one stderr line names the model and pool; a role with no pool is refused, registering and launching nothing. `--requires` is still accepted with any value and ignored; both `create-agent` and `create-agent-legacy` print one line, `--requires ignored: capability requirements were removed on 2026-11-15.`, and launch exactly as without it. A new `spawn.json` has no `capability` field, and an older record that still carries one is listed, resumed and reaped as before. `derive-shadow-name-from-alpha` gives the canonical Shadow name for an Alpha and slice. `list-harnesses-and-models` and `check-config` show the pools and each role's model and effort; `check-config` also shows each switch of the `features` section of `config.user.ts` with its value and its default of off, plus one line when a leftover `~/.throne/config/features.json` exists saying it is no longer read and may be deleted and naming any live switch it still turns on, and for each harness in the `harnessEnvironment` section the names of its variables, never their values; and the key names of the `piSettings` section, never their values.

The `harnessEnvironment` section of `config.user.ts` maps a harness name to variables, each a string, that every agent launched on that harness gets in its process. It is read afresh on every launch, so creation, `restart-harnesses`, revival and the Regent's own launch all pick up a change, and a running agent sees it only after a restart. throne's own values win over a configured variable of the same name. Loading refuses, naming the key, a value that is not a string, a name that is not a known harness, and a reserved variable: any name starting `THRONE_`, `GIT_` or `HERDR_`, `PATH`, `HOME`, `CLAUDE_BIN` and `CODEX_BIN`. When the file cannot be loaded at launch, the agent launches without the extra variables and one stderr line says so.

A new Claude agent is launched with `--plugin-dir extensions/claude` when the installed Claude Code passes `claude plugin validate` on that folder, and `spawn.json` records `claude_mod: true`; otherwise it launches without the mod, records `claude_mod: false`, and the failed validate prints one line saying the mod does not fit that version. A pass is remembered in `claude-mod-fit.txt` in throne's cache folder, keyed by the Claude Code version and the mod's file contents, so validate runs again only when either changes; a failure is never remembered. A Claude agent with the mod and every pi agent get a delivery socket path, chosen under the real throne home and refused at launch when over 100 bytes, recorded in `spawn.json` as `delivery_socket` and passed as `THRONE_DELIVERY_SOCKET`; a Claude agent also gets `THRONE_DELIVERY_RUNTIME` and `THRONE_DELIVERY_HELPER`, the absolute paths of `bin/throne-runtime` and the mod's helper. Both also get `THRONE_DELIVERY_CALLBACK`, the backend's callback socket `<throne home>/delivery-callback.sock`, recorded in `spawn.json` as `delivery_callback`, so the agent can report each accepted message's outcome (MSG-CLAUDE-MOD, MSG-PI). A restart or revival passes the recorded paths again. Codex and other harnesses launch with the same argv as before and get no socket.

Before a Claude agent launches, one locked write to the Claude account config it launches under, the primary `~/.claude.json` or a secondary account's own, sets `hasTrustDialogAccepted: true` on its worktree and on the git top-level of the global skills folder: `~/.claude/skills` followed to its real path, two folders up, then `git rev-parse --show-toplevel`, so no "Adding a new directory" prompt appears for the skills folder passed with `--add-dir`, whatever that repository is called. No link, a broken link, or a folder outside any git repository adds nothing and the launch goes on. When both are already trusted the grant takes no lock and leaves the file byte-identical.

The `pi` harness runs only DeepSeek, as `pi/flash` (a bare `pi`) and `pi/pro`, admitted wherever claude is; any other pi pair is refused. The omp harness is gone: naming it to `create-agent`, `create-agent-legacy`, in a `config.user.ts` pool, preset or active harness, or in a stored record is refused with `the omp harness was removed from the throne; use the pi harness instead`. At launch each name resolves to the newest DeepSeek model of its family, else the day cache, else a pinned id, and the launch output names the id and where it came from. The launch is refused, launching nothing, when the DeepSeek provider account is missing or its key file is missing, empty or wider than mode 600. pi starts through `bin/piy` on the pinned Bun with the key only as `DEEPSEEK_API_KEY` in the pane environment, its own `pi-agent/` and `pi-sessions/` folders under the ledger, and the delivery and state extensions installed there. The launched pi's `settings.json` is throne's quiet defaults with `defaultTools: ['+codemode']`, which turns pi's codemode on, then `~/.throne/config/pi-settings.json`, then the `piSettings` section of `config.user.ts`, then throne's skill folders, provider and model, so `piSettings` wins over `pi-settings.json` for the same key and a `defaultTools` naming tools without `+codemode` turns codemode off. `piSettings` is read afresh at every pi launch, the same tolerant way as `harnessEnvironment`, so a running pi keeps its old settings until relaunched. Loading refuses, naming the key, a `piSettings` that is not a plain object, a value that is not JSON, and `defaultProvider` or `defaultModel`; pi's own setting names are not checked. Without the section the file is exactly as before. `spawn.json` records the pi session id, model id, display name and account, never the key. The launched pi's `models.json` holds a deepseek provider entry only when it has something in it (a base URL or a custom model); a built-in model with no base URL gets `{"providers":{}}`, since pi refuses an empty provider entry with a red models.json error. pi parses each skill's SKILL.md frontmatter as strict YAML and drops one that fails, so every throne skill's frontmatter parses that way with a description of at most 1024 characters.

A new Stager's opening prompt tells it to file a consolidated plan with `add-to-queue` and then tell the Regent the item was added, naming the objective code, as a statement of fact: it never asks the Regent to launch the Alpha and never launches one itself, as `agent_docs/role-stager.md` says. An Alpha spawn refused for its supervisor says to file the plan with `add-to-queue` and notify the Regent, who decides when to launch.

A fork made with `--topic-from <origin>` is refused unless the fork is created with `--role Stager --supervisor Regent`, the origin is a live Stager, and the origin's latest line in `topic-verdicts.jsonl` is `changed`; the refusal names the origin, and there is no `--fork-of` alias. Before its identity is written, create-agent copies the Lord's last prompt typed at or before that verdict, verbatim from the origin's Claude transcript, into `data/<fork>/lord-prompt.md`. A typed prompt is a `user` entry of human origin with text content, or a human-origin `queued_command` attachment typed mid-turn; plugin deliveries, tool results and meta entries never count. The fork's identity then says it acts on that `lord-prompt.md` as the Lord's own word, `add-to-queue` included, names the Regent as supervisor and no parent, and its opening prompt tells it to read that file and act on it. With a non-Claude origin, a missing transcript or no typed prompt, nothing is copied; any failure in the copy never stops the launch.

An Alpha created with a campaign objective takes that campaign's queue row as soon as its opening prompt is delivered, and a failed launch gives back the row held under its name (QS-ALPHA-TIE). Any other role, in `create-agent` and `create-agent-legacy` alike, never touches the queue.

## Sub-features

- CA-POLICY: Role-pool admission is the hard gate outside steering; `--requires` is accepted, ignored and announced in one line.
- CA-POOL-MODEL: With no `--model`, create-agent takes the first model of the role's active pool, and refuses a role with no pool.
- CA-LEDGER: Identity and spawn evidence are persisted before launch.
- CA-SHADOW-NAME: A Shadow name is derived from its Alpha name and slice id.
- CA-FORK-NAME: `--topic-from <origin>` accepts any valid name for the fork; it need not begin with the origin's name, so a Stager forks `stager-<topic>` (`src/create-agent/topic-from.spec.ts`).
- CA-CLAUDE-MOD: A Claude agent launches with throne's mod whenever the mod validates, spawn.json records which and its delivery socket, and its opening prompt and its first colour and name correction then go over that socket (MSG-CLAUDE-MOD, BE-SETTINGS).
- CA-SKILLS-TRUST: A Claude spawn marks the git repository holding `~/.claude/skills` trusted in the same locked config write as its worktree, for the primary and any secondary account config, adds nothing when the link is missing, broken or outside git, and rewrites nothing when both are already trusted (`src/claude-spawn-trust/claude-worktree-trust.test.ts`).
- CA-PI: pi/flash and pi/pro launch on the newest DeepSeek model through bin/piy with the provider key, refused when the key is not ready, with a delivery socket recorded in spawn.json and passed to the extension (MSG-PI).
- CA-OMP-REMOVED: The removed omp harness is refused wherever it is named, and the refusal points at pi.
- CA-PI-RECORD: A pi spawn records its session id and model id, and a resume reuses them without resolving again.
- CA-PI-SETTINGS: A pi launch writes throne's quiet defaults, including `defaultTools: ['+codemode']`, into the launched pi's `settings.json`, with the user's `~/.throne/config/pi-settings.json` laid over them, then the `piSettings` section of `config.user.ts`, which wins for the same key and refuses `defaultProvider` and `defaultModel` at load; the provider and model stay throne's, and a file that is not one JSON object refuses the launch (docs/CONFIG.md "pi settings"; `test/pi-models-newest-model.test.ts`, `test/pi-launch-wiring.test.ts`, `src/create-agent/pi-settings.spec.ts`).
- CA-PI-SKILLS: A pi launch names throne's `.claude/skills` folder under `skills` in the launched pi's `settings.json`, so the agent has throne's skills in any working folder, with no project trust; the user's own `skills` folders are added after it (`test/pi-models-newest-model.test.ts`, `test/pi-launch-wiring.test.ts`; checked on a real pi with `get_commands` in RPC mode from a folder outside the checkout).
- CA-PI-MODELS-JSON: A pi launch on a built-in model with no base URL writes a `models.json` with no provider entries, so pi starts with no models.json error (`test/pi-models-newest-model.test.ts`).
- CA-SKILL-FRONTMATTER: Every `.claude/skills/*/SKILL.md` frontmatter parses as strict YAML with a description of at most 1024 characters, so pi loads every skill (`test/every-skill-frontmatter-parses-as-strict-yaml-with-a-short-description.test.ts`).
- CA-DRIFT-FORK: A fork made after its origin's `throne topic changed`, which launches it itself, starts with `lord-prompt.md` holding the Lord's verbatim drift prompt and identity and opening-prompt text telling it to act on it; after `same` the fork is refused (`src/create-agent/drift-prompt.spec.ts`, `src/create-agent/drift-fork-launch.spec.ts`).
- CA-STAGER-PROMPT: The Stager opening prompt says to file with `add-to-queue` and notify the Regent as a statement of fact, never to ask for a launch.
- CA-PI-INSTRUCTIONS: A pi launch links throne's `extensions/pi/AGENTS.md` into the launched pi's agent folder as `AGENTS.md`, in the same step as the delivery extension, and a launch that cannot place it is refused with the reason and launches nothing (docs/CONFIG.md "pi settings"; `test/pi-launch-wiring.test.ts`).
- CA-HARNESS-ENV: Variables configured per harness under `harnessEnvironment` reach every agent launched on that harness, beneath throne's own values; every Claude agent starts with `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1` laid beneath the section, so `harnessEnvironment: { claude: { CLAUDE_CODE_EXPERIMENTAL_CODE_MODE: '0' } }` turns code mode off, and codex and pi get no such variable; reserved names, unknown harnesses and non-string values are refused at load (docs/CONFIG.md; `src/harness-environment.spec.ts`, `src/herdr/herdr-launch.spec.ts`).
- CA-QUEUE-ROW: Only an Alpha takes a queue row, at tasking; a failed launch reopens it (`test/a-row-release-reports-the-real-row-state.test.ts`).
- CA-CONFIG: check-config validates config.user.ts and prints each role's model, each harness's configured variable names, the `piSettings` key names, and each `features` switch with its default; a `features` value that is not a boolean, or a key throne does not know, refuses the file naming the key.

## How to reach it and prove it works

Take the name of a live Alpha from `throne agent-statuses`, for example `alpha-<code>-01`, then:

```
throne derive-shadow-name-from-alpha alpha-<code>-01 06
```

Prints `shadow-<code>-06` and exits 0. With an Alpha name that has no spawn evidence it exits 1 and says so; with no arguments it exits 1 and names what is required.

## Gotchas

The derive command takes positional arguments only; flags are refused. It reads the Alpha's spawn evidence from the ledger, so it works only for a registered Alpha.

The mod launch is proven by `bun test ./test/claude-mod-launch.test.ts ./test/claude-mod-passes-validate-and-its-own-tests.test.ts`, which exits 0.

A pi launch needs pi vendored by `install.sh`; without it `piy` exits saying no pi was found. pi's print mode exits 1 silently when stdin is an open pipe. The pi lines are proven by `bun test ./test/pi-harness.test.ts ./test/pi-launch-wiring.test.ts ./test/pi-models-newest-model.test.ts ./test/piy-launcher.test.ts` and `bun scripts/pi-evidence/run.mjs --all` against the local DeepSeek stand-in. Its `flows` group holds six whole-product flows (F1 to F6: a pi Shadow on flash and on pro, a pi Alpha spawning a Shadow, a waiting agent woken once, Claude and pi Shadows each getting only their own messages, and a launch refused without the DeepSeek account), which run only with `--real-provider`, read the key from the throne accounts folder at `pi/deepseek/api-key`, and report the tokens each line spent and the run total in `pi-evidence.json`.
